# Ghost System and Module Promotion Lineage

Status: first-pass provenance reconstruction

Provenance state: `CONFIRMED_INTERNAL`, `CONVERGENT`

## Shared Origin Problem

Ghost System and Module Lab answer two related questions:

1. How can Velvet demonstrate, rehearse, and recover system behaviour without touching live hardware?
2. How can new code earn a place in the body without self-installing, hiding authority, or being trusted merely because it runs?

Both grew from the need for public demonstrations, archive recovery, incomplete hardware, hot-swappable modules, and strict physical boundaries.

## 1. Ghost System

### Recovered Purpose

Ghost System v0 provided a sealed public path through:

```text
synthetic or replayed CAN
  -> decoding
  -> Event Protocol
  -> AI Core proposal
  -> Runtime routing
  -> Interface display
  -> Receipts and continuity evidence
```

The path explicitly declared that it did not:

- open a physical vehicle bus
- transmit CAN frames
- actuate hardware
- grant authority
- convert replay into live execution

### Recovered Public History

Verified commits include:

- `24fd5bccf8c94f530b4afd2a187bf8c853250ce5` in `velvet-vehicle-can` for the Ghost Car CAN demo
- `95ab583b50c5d65cdb5b7d0ba9d6acdf31819ec4` in `velvet-ai-core` for the Ghost Car proposal layer
- `e42a6997f8480994a58317a01942f7281dabfe60` in `velvet-docs` for Ghost System v0 documentation
- `d06bdd6df57b563b6d7055cd9b82bb5a54eff4cb` in `velvet-docs` for distributed end-to-end Ghost integration
- `73c75c4c1751fe06298de48b8c94716ce45a82eb` in `velvet-ai-core` for the restored Native Brain Ghost cognition loop

### Internal Development Pressures

- the physical Tiburon and UP Squared were not always available
- GitHub interruptions and archive fragmentation required recoverable public demonstrations
- private code could not be published wholesale
- the system needed proof that public demos were physically sterile
- cross-repository contracts needed end-to-end tests
- the Native Brain required a safe source of realistic events

### Convergent Families

Ghost is convergent with:

- deterministic replay
- simulation harnesses
- software-in-the-loop testing
- record-and-replay debugging
- synthetic telemetry
- public demo wrappers
- disaster-recovery exercises
- reference implementations

No single outside replay framework is currently proven as its origin.

### Adopt / Adapt / Reject

Adopt:

- fixed fixtures
- deterministic outputs
- explicit replay state
- cross-repository integration tests
- read-only demonstration paths
- evidence that physical execution stayed disabled

Adapt:

- record-and-replay into a public-safe version of a private physical system
- simulation into a continuity and recovery tool
- synthetic CAN into a body-wide protocol test

Reject:

- replay frames reaching live CAN writers
- Ghost credentials being accepted as physical identity
- demo success being treated as road-safety proof
- hidden dependencies on private repositories
- simulated receipts claiming physical consequence

## 2. Module Lab and Promotion Gates

### Recovered Purpose

Module Lab is the place where a candidate organ proves why it deserves to join the body.

The public contribution path and private qualification concept existed before executable gates were added. The strongest current evidence is:

- the surviving module-archaeology audit, which records unsafe automatic discovery, broken loader generations, direct-control quarantine, and the need to rebuild candidates behind modern contracts
- AI Core commit `7dbee418f60484a704f90f0369c5cdb39b1d44fb`, which added executable promotion gates, authority-bypass tests, failure injection, and promotion evidence

Earlier contribution-path commits may be added later when their exact role and repository context are individually verified. They are not required to establish the current lineage.

### Internal Laws

- modules are explicitly registered; Velvet does not scan storage looking for organs
- installation does not equal activation
- activation does not equal authority
- modules advertise capability and limits
- simulated evidence remains marked simulated
- promotion requires tests, receipts, and review
- failure, overload, stale dependencies, and authority-smuggling attempts must be visible
- rollback and quarantine are healthy states
- a module cannot promote itself

### Convergent Families

Module Lab is convergent with:

- staging environments
- package signing and software supply-chain review
- plugin sandboxes
- quarantine
- canary releases
- CI promotion gates
- admission controllers
- safety-case evidence
- hardware qualification benches

No single package manager, orchestrator, or software-supply-chain framework is currently proven as the source.

### Adopt / Adapt / Reject

Adopt:

- explicit registration
- lifecycle states
- dependency declarations
- test evidence
- compatibility matrices
- quarantine and retirement
- rollback checkpoints
- reviewable promotion receipts

Adapt:

- software release gates into organ admission for a physical AI body
- plugin trust into two-sided module and body verification
- CI evidence into local promotion decisions requiring owner presence when trust changes
- hardware qualification into simulated and bench evidence packs

Reject:

- filesystem discovery as module registration
- self-installation
- self-promotion
- unsigned or unexplained authority
- hidden executor access
- passing unit tests as sufficient physical approval
- promotion that erases prior failures

## Shared Relationship

Ghost provides a sterile body in which a module can demonstrate behaviour.

Module Lab decides whether the evidence is sufficient for later promotion.

Neither system grants physical authority.

```text
candidate module
  -> declared contract
  -> Ghost or Simulated Body exercise
  -> failure and abuse tests
  -> promotion evidence
  -> external review and approval
  -> bounded registration
  -> Runtime and Court remain authoritative
```

## Current Attribution

The correct current statement is:

> Ghost System and Module Lab are confirmed internal Velvet mechanisms developed for safe demonstration, recovery, testing, and organ promotion. They are convergent with deterministic replay, SIL/HIL, staging, quarantine, CI admission, and software-supply-chain assurance, but no single external origin is proven.
